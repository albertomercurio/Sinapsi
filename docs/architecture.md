# Architecture

## Overview

```
Browser (static SPA, Cloudflare)  ──HTTPS──▶  Supabase, eu-central-1 (Frankfurt)
  Vue 3 + Vite                                 ├─ Postgres: tables, RLS, RPCs, audit, pg_cron
  vue-i18n (precompiled)                       ├─ Auth: email + password, TOTP MFA, invites
  ECharts (lazy)                               ├─ Data API (PostgREST): explicit grants only
                                               └─ Edge Function admin-invite (service role)
```

The static host only serves files. Every request carrying personal or health data goes from the
browser straight to Supabase in Frankfurt (the CSP `connect-src` allows nothing else).

```
    measurement     TrialRecorder, kinematics, device info, compressed event logs, quality flags
    scoring         statistics library (SDT, ex-Gaussian, trends, Glicko, staircase…)
    sessions        builder, templates, agenda, clinic runner (patient mode + PIN)
    results         analysis, charts (ECharts), run detail, replay, report, CSV
    settings        profile, 2FA devices, practice, encrypted backup, audit log
    admin           platform admin console (organizations, invitations, storage)
  activities/<id>/  activity plugins: index.ts, logic.ts (pure), Player.vue, Print.vue?, locales/
  content/          picture stimuli (language-neutral) + words per language
  locales/          global messages (common, errors, metrics)
supabase/
  migrations/       schema, RLS, grants (one file), RPCs, restore
  functions/        admin-invite
  tests/database/   pgTAP security tests
  seed.sql          synthetic local data
e2e/                Playwright (runs against `vite preview` + local Supabase)
scripts/            i18n check, admin backup, demo-data simulator
```

**Adding a feature module** = a folder in `src/modules` with an `index.ts`, plus one line in
`src/app/modules.ts`. Translations in `src/modules/<id>/locales/*.json` are discovered
automatically under the `<id>.` namespace.

## Security model

| Layer | Rule |
|---|---|
| Data API | `auto_expose_new_tables = false`; every privilege is granted in `20261017000004_grants.sql`. `anon` can only call `ping()`. Column-level grants stop clients from writing `org_id`, `code`, `created_by`. |
| RLS | Every table: a **restrictive** policy requiring `aal2` (TOTP completed) + permissive member policies scoped by `org_id`. No policy gives platform admins clinical rows. |
| Patients | No name/DOB columns; `code` must match `^[A-Z]{1,4}-[A-Z0-9]{4,8}$` and is generated by a trigger. |
| Child rows | `org_id` is inherited from the parent by triggers — a client can never choose it. |
| Destructive actions | Patient hard delete: owners only, must retype the code (`delete_patient`). Runs are immutable. |
| Audit | `audit_log` is append-only (no grants), filled by triggers (column names only, never values) and by `log_event` for exports/backups/prints. |
| Edge Function | `admin-invite` verifies the JWT, requires `aal2`, checks platform-admin/owner role, then uses the service role. Invoke with `region: eu-central-1`. |
| Browser | Strict CSP (`script-src 'self'`, `style-src 'self'`, no eval thanks to precompiled i18n), HSTS, no referrer, no third-party requests, idle logout, patient-mode PIN lock. |

The pgTAP suite (`pnpm test:db`) proves these rules (51 assertions).

## Data flow of a run

1. `SessionRunnerPage` loads the session and the patient's abilities; `chooseDifficulty` picks the
   level (therapist lock → fixed item difficulty → Glicko target success).
2. `ActivityHost` validates the config (`zod`), generates the instance from a random **seed**, runs
   the optional motor baseline, then the activity `Player`, which records into `TrialRecorder`.
3. On completion the activity's pure `score()` returns metrics, a 0–100 score and a graded
   `performance` (or item-level outcomes); quality flags are added.
4. `saveCompletedRun` computes the new ability and calls `record_activity_run`, which stores the
   summary, the deflate-compressed raw events and the ability in one transaction.
5. Raw events expire after the organization's retention (pg_cron job, default 24 months); summary
   metrics stay. Because seed + events are kept, runs can be **re-scored** when a formula changes
   (`scoring_version`).
